# Миграции

## Инструмент

Проект использует `golang-migrate` через локальный CLI `cmd/migrate`.

Основной код:

- `data/mysql/migrator.go`
- `cmd/migrate/main.go`

Путь миграций:

- `data/mysql/migrations`

## Создание миграции

```bash
./bin/create-migration.sh add_some_change
```

Скрипт создаёт пару файлов:

- `..._add_some_change.up.sql`
- `..._add_some_change.down.sql`

## Локальное применение

Через Docker окружение:

```bash
./bin/dorm-migrate.sh
```

Или напрямую через бинарник:

```bash
go run ./cmd/migrate up
```

## Поддерживаемые команды CLI

Ниже перечислен синтаксис, а не рекомендуемая последовательность выполнения. Для force переменная VERSION должна содержать целую версию, выбранную после ручного аудита схемы.

```bash
go run ./cmd/migrate up
go run ./cmd/migrate down
go run ./cmd/migrate version
go run ./cmd/migrate force "$VERSION"
```

Что делает каждая:

- `up` — применяет все новые миграции;
- `down` — откатывает ровно один шаг;
- `version` — печатает `version=<n> dirty=<bool>`;
- `force` — вручную выставляет версию при dirty-state.

## Почему нельзя менять старые миграции

Применённая миграция уже могла отработать:

- локально у других разработчиков;
- на production;
- на дампах и резервных копиях.

Редактирование старого файла создаёт расхождение между одинаковой версией migration chain и разным фактическим schema state.

Правило проекта: добавлять новую миграцию поверх существующих.

## Требования к `up/down`

- у каждого `up.sql` должен быть `down.sql`;
- `down.sql` должен откатывать схему настолько корректно, насколько это возможно;
- необратимая security migration может намеренно запрещать down: её нельзя представлять как обратимую.

## Проверка schema после миграции

Минимальный цикл:

1. поднять чистую БД;
2. применить `up`;
3. проверить нужные таблицы и индексы;
4. по возможности выполнить критические репозитории/use-case;
5. при необходимости проверить `down` на тестовой базе.

Практически:

```bash
./bin/dorm-up.sh
./bin/dorm-db.sh
```

Дальше можно использовать SQL вроде:

```sql
SHOW CREATE TABLE duty;
SHOW INDEX FROM team;
```

## Dirty migration

Проверка версии:

```bash
go run ./cmd/migrate version
```

Если `dirty=true`, сначала исследуют фактическую схему, продолжающийся DDL и состояние данных. Следующая команда показана как синтаксис ручного инструмента, а не способ автоматического исправления:

```bash
go run ./cmd/migrate force "$VERSION"
```

`force` исправляет служебную версию migration table, но не чинит схему сам по себе.

## Production flow

Release manager запускает migrate из versioned image с обоими production Compose и assets override. Рабочий каталог и env — конкретный релиз, project dorm. SQL up идёт после штатного backup и до switch. Не запускайте вручную отдельный Compose без этих проверок вместо release manager.

Обычный backend имеет MySQL readTimeout 30 секунд, migrator — 10 минут; connect timeout и PingContext — 5 секунд, writeTimeout — 15. Внешний timeout Compose для up — 900 секунд, для прочих команд обычно 180. Timeout клиента не доказывает завершение DDL на сервере. После ошибки release manager сохраняет backup, сообщает stage/dirty и не выполняет retry/down/force/restore автоматически.

## `1795059644_auth_sessions`

Миграция содержит:

1. Временную preflight-таблицу с CHECK и проверку дублирующихся активных логинов. Конфликты требуют ручного решения, данные автоматически не исправляются.
2. `auth_session` с PK хеша токена, FK user и индексами пользователя/срока.
3. Уникальный функциональный `uq_active_user_login`, игнорирующий soft-deleted пользователей.

Сессии и уникальный индекс — постоянная часть схемы. История применённых миграций сохраняется; воспроизводимость новой установки не требует поддержки старых алгоритмов паролей.

Down этой миграции намеренно содержит SIGNAL об ошибке: схема серверных сессий — forward-only. Этот запрет сохранён. DDL MySQL может фиксироваться отдельно от последующих операторов, поэтому ошибка не означает откат всей схемы. Пароли создаются и меняются штатными операциями приложения, SQL-миграция их не преобразует.

`force` только меняет служебную версию, не чинит таблицы, credentials или сессии. `down`, force и restore dump не являются автоматическим восстановлением после неудачного DDL. Нужны проверенные forward-изменения и повторная readiness-проверка. Новые миграции создают парой через create-migration.sh; уже применённые файлы не редактируют.
