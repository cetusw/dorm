# Резервное копирование и восстановление

## Backup при deployment

Каждый `bin/deploy.sh user@host` создаёт один серверный архив перед остановкой backend и SQL-миграциями. Отдельной команды backup в проекте нет. Каталог — `/home/<SSH-user>/dorm/backups/`, имя — `dorm-backup-YYYYMMDD-HHMMSS-XXXXXX.sql.gz`. Путь выводится при успехе и в диагностике ошибок. Предыдущие архивы не удаляются и не перезаписываются; скачивание не автоматизировано.

Проверяются SELECT 1, свободное место (двойная оценка размера БД плюс 64 MiB), завершение mysqldump/gzip с pipefail, непустой архив, gzip -t и читаемая схема. Дамп содержит single-transaction, quick, hex-blob, routines/events/triggers, --databases; пароль берётся из окружения контейнера. Конвейер ограничен 1800 секундами. Публикация не заменяет существующий файл, файл/каталог синхронизируются. Ошибка блокирует остановку/миграцию/обновление backend. Это проверка архива, а не полный тест восстановления.

Скопировать выбранный архив на защищённую локальную машину можно отдельно:

```bash
scp admin@server:/home/admin/dorm/backups/dorm-backup-YYYYMMDD-HHMMSS-XXXXXX.sql.gz ./backups/
gzip -t ./backups/dorm-backup-YYYYMMDD-HHMMSS-XXXXXX.sql.gz
```

Замените имя фактически созданным, заранее создайте закрытый локальный backups/ и не перезаписывайте свою копию. Архив содержит password hashes и состояние сессий; храните защищённую off-host копию.

Deploy не останавливает внешних writers. InnoDB snapshot не включает последующие записи; конкурентный DDL может нарушить согласованность. Для отдельного согласованного backup администратор планирует maintenance и штатный mysqldump вручную. Нельзя запускать такие операции одновременно с deploy: используйте ту же `.deployment.lock` и исключите writes на весь интервал.

## Ручное восстановление

Автоматического restore нет. Импорт может удалить/заменить таблицы и credentials: выполняйте его только на специально выбранной изолированной БД либо по отдельно проверенному production-плану с остановленными writers и собственной свежей резервной копией. Не импортируйте неизвестный dump в работающую установку.

Безопасный первый шаг — проверить копию и восстановить её в отдельное тестовое MySQL-окружение, не подключённое к production-сети. Для уже созданного disposable-контейнера с настроенным MYSQL_ROOT_PASSWORD:

```bash
gzip -t /absolute/path/backup.sql.gz
set -o pipefail
gzip -dc /absolute/path/backup.sql.gz | docker exec -i dorm-restore-db sh -c 'export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"; exec mysql -uroot --default-character-set=utf8mb4'
```

`dorm-restore-db` здесь — заранее выделенная тестовая БД, не dorm-db. Дамп содержит CREATE DATABASE/USE и может содержать DROP TABLE: указание другой базы аргументом mysql не перенаправляет его в безопасное место. Сначала проверьте содержимое и назначение окружения; не включайте вывод чувствительных INSERT в логи.

После импорта сверяют schema_migrations (version/dirty), фактические таблицы/индексы, количество и связи пользователей, дежурств, задач, предупреждений, движений склада и уведомлений. Запускают выбранный production-образ на изолированной копии: при старте CheckPasswordReadiness проверяет уникальность активных логинов и формат всех Argon2id-хешей. Затем проверяют login/me/logout и protected API. Одна лишь проверка COUNT или gzip не подтверждает восстановление.

## Совместимость восстановленных данных

Перед запуском проверьте совместимость фактической схемы, данных и выбранного Docker-образа. Deploy проверяет SQL version/dirty, но не доказывает произвольную совместимость данных и старых образов. Production-backend отказывается запускаться с некорректным password hash или дублирующимися активными логинами. Утилиты преобразования устаревших паролей больше нет: используйте проверенную актуальную резервную копию либо отдельный согласованный план исправления данных. Не применяйте force/down как универсальный repair.

Восстановление auth_session возвращает снимок состояния сессий: отозванная после даты backup сессия потенциально снова станет активной; сессии, созданные позднее, пропадут. Нельзя считать восстановленные сессии безопасными без отдельного решения об их отзыве. Истёкшие сроки и soft delete проверяются по восстановленным данным; удалённый после backup пользователь может появиться снова. Проверка и при необходимости отзыв восстановленных сессий — часть ручного плана, не автоматическая функция deploy.

В production восстановление БД и повторный старт согласуют отдельно. Автоматического rollback приложения или БД нет; перед запуском выбранного образа требуется отдельная проверка совместимости. См. [deployment](./deployment.md).
