# Предупреждения (`Penalty`)

## Терминология

В UI используется слово «Предупреждение». В backend feature по-прежнему называется `penalty`, но основная запись теперь является журналом операций `penalty_entry`.

## Назначение

Предупреждения больше не моделируются как отдельные активные/разрешённые сущности.

Система хранит журнал изменений общего баланса жителя:

- `ISSUE` увеличивает баланс предупреждений;
- `RESOLVE` уменьшает баланс предупреждений;
- снятие предупреждения не относится к конкретной ранее выданной записи.

## Модель

Поля `penalty_entry`:

- `user_id`
- `type`
- `weight`
- `reason`
- `created_at`

`weight` всегда хранится положительным. Знак изменения определяется только `type`.

Пример истории:

- `ISSUE 1.0 "Не выполнена уборка"`
- `ISSUE 1.0 "Не убрана кухня"`
- `RESOLVE 0.5 "Выполнено дополнительное задание"`

Текущий баланс:

- `1.0 + 1.0 - 0.5 = 1.5`

## Инварианты

- `weight >= 0.1`
- `weight` округляется до одного знака после запятой
- `reason` обязателен и ограничен 256 символами
- `type` допускает только `ISSUE` и `RESOLVE`
- после любой операции итоговый баланс жителя не может быть меньше `0`

## Права доступа

### Глава общежития

Видит и управляет предупреждениями жителей своего общежития.

Scope строится по `dormitory.leader_id`.

### Глава группы

Если пользователь не глава общежития, сервис пытается выдать scope главы группы:

- находит все группы его текущего общежития
- проверяет, что он является главой хотя бы одной из них
- если да, даёт тот же scope, что и главе текущего общежития: всех жителей этого общежития

### Кто не может

- обычный житель
- глава команды без лидерства группы
- пользователь без `dormitory_id`

## Правила выдачи

Создание предупреждения:

1. проверить scope текущего пользователя
2. убедиться, что целевой житель находится в доступном scope
3. нормализовать `reason` и `weight`
4. создать запись `ISSUE`

## Правила снятия

`ResolvePenalty`:

1. проверяет scope и доступность жителя
2. нормализует `reason` и `weight`
3. в одной DB-транзакции блокирует строку жителя
4. считает текущий баланс по всему журналу
5. если `weight > balance`, возвращает ошибку
6. иначе создаёт новую запись `RESOLVE`

Операция `RESOLVE` не ссылается на конкретный `ISSUE`.

## Исправление записей

Глава общежития или группы может отредактировать причину и вес записи либо удалить её. Тип и дата записи при редактировании не меняются.

Перед изменением или удалением repository в транзакции блокирует жителя и проверяет, что итоговый баланс по оставшейся истории не станет отрицательным.

## Суммарный вес и threshold

Баланс считается по всей истории жителя:

- `SUM(ISSUE.weight) - SUM(RESOLVE.weight)`

Текущий UI-флаг:

- `threshold_reached = total_weight >= 6`

Это read-model индикатор. Отдельной автоматической санкции в backend нет.

## Миграция старых данных

Старая таблица `penalty` мигрируется в `penalty_entry` так:

- каждая старая запись становится `ISSUE`
- если старая запись была разрешена (`resolved_at IS NOT NULL`), создаётся дополнительная запись `RESOLVE` того же веса на момент `resolved_at`

Это сохраняет итоговый баланс пользователей и факт снятия предупреждения, хотя старая модель не позволяла выразить частичное снятие как отдельную историческую операцию.

Откат миграции восстанавливает только записи `ISSUE`: старая схема не может представить частичные `RESOLVE`, поэтому их история при rollback не сохраняется.
